00 / Punto de partida

Cómo trabajar con esta guía

Esta edición sustituye la infraestructura AWS por un solo servidor virtual DigitalOcean Droplet. El mismo código Python integra las cuatro variables del Arduino UNO R4 WiFi, un broker Mosquitto, MongoDB y un dashboard con alarmas. Se entregan todos los archivos: no es necesario programar desde cero ni contratar un registro de imágenes.

ZIP junto a la guía

El primer botón extrae el ZIP incorporado al HTML. El segundo es opcional, si publica también el ZIP junto a este archivo. La guía funciona sin bibliotecas externas; descargar imágenes Docker y utilizar DigitalOcean requiere Internet.

A · Local (recomendado)Instalar Docker, construir, simular y probar.
B · DropletCrear una VM, transferir código, instalar y operar.
C · Arduino remotoElegir túnel de laboratorio o TLS directo.
Ruta corta: si dispone de un único Droplet y desea evitar instalar Docker localmente, lea arquitectura (01), vaya a 07–10, ejecute el simulador remoto y luego siga 11–12. El computador solo necesita navegador, SSH/SCP y Arduino IDE si va a conectar hardware.
Alcance y certeza: se ejecutaron cinco pruebas unitarias del motor de alarmas y revisiones de sintaxis/estructura. No se dispuso de Docker Engine, una cuenta DigitalOcean ni Arduino físico para ejecutar el sistema integral; realice los controles de aceptación. Las etiquetas de imágenes por familia no fijan un digest; los paquetes y pantallas pueden cambiar. No se garantizan prestaciones sin medición.

Seleccione el sistema operativo de su computador

Solo afecta bloques del computador. Todos los comandos etiquetados DROPLET son Ubuntu y se ejecutan en sesión SSH, sin importar el sistema local.

Convenciones: PC = su computador; DROPLET = terminal conectado por SSH. Sustituya IP_DROPLET, IP_LAN_PC y mqtt.ejemplo.cl por valores reales. No copie símbolos de prompt. No incluya credenciales en GitHub. En local Linux puede necesitar sudo; en el Droplet los comandos Docker lo incluyen deliberadamente.

Para la ruta local se recomienda 8 GB de RAM y 10 GB de espacio libre como referencia inicial. Windows: Docker Desktop/WSL2 y virtualización habilitada; Linux: Ubuntu 24.04 LTS como ejemplo.

Qué se construye y qué se reutiliza

ConceptoFunción y ejemplo
Imagen DockerPaquete de software, por ejemplo irrigation:1.0.0. Una imagen sirve para dashboard, worker y simulador, usando comandos distintos.
ContenedorInstancia ejecutable de una imagen. Se inician cuatro servicios permanentes, más el simulador temporal.
Docker ComposeDescribe servicios, redes, puertos, credenciales y volúmenes en YAML.
MongoDBBase de datos documental NoSQL. No se expone el puerto 27017.

MongoDB es representativa de sistemas de documentos reales y permite consultas, índices y persistencia histórica. TinyDB es más liviana, pero no es una buena elección para escrituras concurrentes desde procesos separados; InfluxDB es otra buena opción especializada en series temporales; Para este laboratorio no se necesita una base de datos administrada. NoSQL no es un requisito universal de IoT. Para un nodo con un mensaje cada 30 s: 2.880 documentos/día y 1.051.200/año; cada documento contiene cuatro valores. Con 300 bytes/documento serían 315 MB/año de datos brutos, sin índices, compresión ni overhead. Este proyecto almacena también estados y reglas en cada documento, por lo que el tamaño real probablemente sea mayor. Medirlo antes de dimensionar.

¿Un contenedor, tres o cuatro?

DiseñoEvaluación
Uno monolíticoPosible con un supervisor, pero complica arranque, salud, actualizaciones y persistencia.
Tres contenedoresBroker + DB + Python con web y receptor en un único proceso o supervisor; requiere cuidar que no haya suscripciones duplicadas por workers WSGI.
Cuatro contenedores (seleccionado)Separación de tareas; dashboard y MQTT worker usan la misma imagen Python. Tres imágenes en total, un solo Droplet, una única orden Compose.

El Droplet no ejecuta cuatro máquinas virtuales: los contenedores comparten el kernel y el presupuesto de recursos de Ubuntu. No hay ECR ni AMI; se construye localmente en el Droplet con el Dockerfile.

Instalar Docker y herramientas

Windows · PowerShell con Docker Desktop (Linux containers)

  1. Verifique virtualización en Administrador de tareas → Rendimiento → CPU. Si está deshabilitada, consulte al administrador del equipo.
  2. En PowerShell como administrador, compruebe WSL. Si no está instalado, utilice el comando indicado y reinicie si Windows lo solicita.
wsl --status

Solo si WSL no está instalado:

Instale Docker Engine mediante el repositorio oficial. Alternativamente, Docker Desktop para Linux si la distribución y el hardware son compatibles. En una instalación existente no desinstale paquetes a ciegas: consulte primero la guía oficial de instalación en Ubuntu. En Ubuntu nuevo:

03 / Primer sistema funcionando

Construir la imagen y levantar los servicios

3.1 Extraer el proyecto

Descargue el ZIP de la sección 00. Cree una carpeta llamada irrigation-droplet, extraiga todo dentro de ella. El ZIP contiene los archivos directamente, sin una carpeta raíz. No arrastre únicamente los archivos visibles: incluya .env.example, .dockerignore y .gitignore. En macOS Finder se pueden mostrar ocultos con Cmd+Shift+.

macOS / Linux

Si descargó a Downloads (o Descargas), ajuste la ruta real. Alternativamente, abra una terminal en la carpeta extraída.

cd ~/Downloads/irrigation-droplet
ls -la
cp .env.example .env

Windows / PowerShell

Set-Location "$HOME\Downloads\irrigation-droplet"
Get-ChildItem -Force
Copy-Item .env.example .env

Debe encontrar Dockerfile, compose.yaml, app/, mosquitto/, mongo-init/ y droplet/. Las contraseñas de .env.example son exclusivamente para pruebas locales aisladas. Nunca use esas contraseñas públicamente ni suba .env a GitHub. Mantenga MQTT_USER=worker pues coincide con la ACL.

3.2 Aprender Docker construyendo

Ejecute desde la carpeta del proyecto en cualquier SO:

docker build -t irrigation:1.0.0 .
docker image ls irrigation

FROM utiliza Python 3.12; COPY incorpora el código; RUN instala dependencias y crea un usuario sin privilegios; CMD ejecuta Gunicorn. Se utiliza otra orden para el worker dentro de Compose. El punto final selecciona el directorio como contexto de build. En el primer build se descargan capas y paquetes. El Dockerfile y las dependencias directas están disponibles en la sección 15.

3.3 Validar Compose y arrancar

docker compose config --quiet
docker compose up -d --wait --wait-timeout 180
docker compose ps
docker compose logs --tail=30 mqtt-worker

Compose descarga las imágenes públicas de Mosquitto y MongoDB si no existen. -d mantiene servicios en segundo plano. --wait comprueba sus estados y health checks; el worker no tiene health check propio, así que revise su log. En docker compose ps espere cuatro servicios en ejecución, MongoDB, broker y dashboard saludables. El worker deberá escribir “Suscripción MQTT confirmada”. El dashboard puede indicar que todavía no hay mediciones.

Abra http://localhost:8080 y, en otra pestaña, http://localhost:8080/health. El segundo endpoint debe responder {"ok":true}.

Control 03: cuatro servicios activos y página de salud correcta. Si aparece error de MongoDB o del puerto, vaya a la sección 13. No use docker compose down -v para solucionar fallas: borra los datos.

04 / Validación con datos sintéticos

Dashboard, histórico y decisiones

No conecte aún el Arduino: primero aislemos los problemas de software. El simulador ejecuta Python en un contenedor temporal de la misma imagen. El mensaje determinista de prueba es humedad 20 %, temperatura 25 °C, EC 2,8 mS/cm y pH 6,7.

docker compose run --rm simulator python simulator.py --once

pH agua6.70 pHNORMAL

Representación de la salida esperada con reglas iniciales intactas. No es una lectura real del Arduino.

Refresque el dashboard; la página consulta cada cinco segundos. Verifique los estados anteriores y una decisión para humedad y conductividad. El histórico genera cuatro gráficas SVG, con tiempos reales de recepción, límites actuales y hasta 5000 muestras por consulta. La base conserva todos los documentos salvo que se configure retención.

4.1 Flujo continuo

docker compose run --rm simulator python simulator.py --interval 5

Deje ese terminal abierto; se generarán valores cada cinco segundos. Para terminarlo utilice Ctrl+C. Las cuatro tarjetas se actualizan y las gráficas muestran el histórico. No ejecute simultáneamente el simulador y el Arduino con el mismo ID de dispositivo, pues mezclaría ambas fuentes.

4.2 Cambiar alarmas

  1. Detenga el simulador continuo. En el dashboard ajuste humedad mínima de 25 a 10 y mantenga máximo 65 e histéresis 3. Pulse Guardar reglas.
  2. Vuelva a publicar la muestra determinista. Humedad 20 debe pasar de LOW a NORMAL si el último estado era LOW, o mantenerse NORMAL.
  3. Cambie el mínimo a 25, publique otra muestra y debe observar LOW.
  4. Pruebe mínimo mayor al máximo: el backend rechaza la regla y conserva la anterior.
  5. Deshabilite una variable, publique y compruebe DISABLED. Restituya valores apropiados para el ejercicio.

4.3 Deduplicación y persistencia

docker compose run --rm simulator python simulator.py --once --boot duplicate-test
docker compose run --rm simulator python simulator.py --once --boot duplicate-test

El mismo boot_id y secuencia, siempre cero para --once, identifican ambas publicaciones como una medición. El histórico debe tener solo un documento adicional respecto del conteo anterior (detenga otras fuentes y use idéntica ventana temporal). Repita con otro identificador si ya había usado duplicate-test.

docker compose down
docker compose up -d --wait --wait-timeout 180

Consulte el histórico y las reglas: deben persistir. Si no llegan muestras durante 90 segundos, se indica “Sin datos recientes”, que no es necesariamente una prueba de que el dispositivo esté apagado. No implica la desaparición de las mediciones previas.

Control 04: las cuatro tarjetas, gráficas, modificación de reglas, eventos, deduplicación y persistencia funcionan. Registre capturas y el resultado de cada prueba antes de conectar hardware.
05 / Integración física

Arduino UNO R4 WiFi y MQTT

Use primero el sketch arduino/uno_r4_demo/uno_r4_demo.ino. Publica valores fijos para comprobar red y protocolo; no mide sensores. La placa UNO R4 WiFi incluye conectividad mediante un módulo ESP32 y usa la librería WiFiS3. No confundir con Arduino UNO R4 Minima.

5.1 Permitir acceso desde la red local

Arduino y PC deben estar en la misma red privada, sin aislamiento Wi-Fi de clientes. Detenga el simulador. En el archivo .env, cambie MQTT_BIND=127.0.0.1 por MQTT_BIND=0.0.0.0 (o la IP LAN concreta si Docker en ese SO permite enlazarla). Mantenga el dashboard en localhost. Reinicie el broker:

docker compose up -d --wait --wait-timeout 180

macOS · IP de la interfaz Wi-Fi

networksetup -listallhardwareports
ipconfig getifaddr en0

Si Wi-Fi corresponde a otra interfaz, reemplace en0. Revise Ajustes → Red → Wi-Fi → Detalles. Permita Docker en el firewall del sistema solo en la red confiable si aparece una solicitud.

Linux · IP del equipo

ip -4 addr

Identifique la interfaz Wi-Fi/Ethernet conectada al Arduino. Docker publica puertos usando reglas propias de firewall; no confíe únicamente en UFW para aislar un puerto publicado. Use una red de laboratorio aislada, sin redirección de puertos del router; para restricciones avanzadas revise las reglas DOCKER-USER y la documentación de firewall de Docker.

Windows · IP del adaptador físico

ipconfig

Seleccione la IPv4 del adaptador Wi-Fi/Ethernet, no la del adaptador virtual WSL. En Windows Defender Firewall permita TCP 1883 en perfil privado y alcance de subred local si hace falta. No habilite perfiles públicos.

MQTT en 1883 no cifra usuario, contraseña ni telemetría. Úselo únicamente en red confiable de laboratorio. No abra el puerto 1883 en el router o Cloud Firewall de DigitalOcean. Si no puede garantizar el aislamiento, omita esta prueba y use TLS.

5.2 Cargar sketch

  1. Conecte el UNO R4 WiFi por USB. Arduino IDE → Boards Manager → instale Arduino UNO R4 Boards. Library Manager → instale ArduinoMqttClient. WiFiS3 forma parte del soporte de la placa.
  2. Seleccione Arduino UNO R4 WiFi y el puerto USB correspondiente. Abra el sketch incluido.
  3. Edite SSID, WIFI_PASSWORD, BROKER (IP del computador), MQTT_PASSWORD (valor de ARDUINO_MQTT_PASSWORD en .env). Use un BOOT_ID distinto para cada reinicio de ensayo, pues la secuencia se reinicia. Esta decisión simplifica el sketch: en una versión real genere un ID de sesión único automáticamente, mediante persistencia o una fuente adecuada de aleatoriedad.
  4. Pulse Verify y Upload. Abra Serial Monitor a 115200 baud. Espere 30 s. Observe el JSON impreso tras recibir PUBACK del broker y verifique el dashboard.

5.4 Sustituir datos sintéticos por lecturas reales

No es correcto asignar pines o ecuaciones universalmente: no se especificaron modelos de sensores. Obtenga datasheets, verifique tensiones (UNO R4 WiFi usa lógica de 5 V), corriente, rango de salida, referencia ADC y aislamiento. Con humedad capacitiva, determine niveles de calibración seco/húmedo; para EC especifique unidad y método, compensación de temperatura y calibración; para pH utilice soluciones buffer y acondicionamiento de alta impedancia adecuados. La humedad expresada en porcentaje de calibración no equivale automáticamente a contenido volumétrico de agua. Muchos módulos EC y pH pueden interferir si comparten el medio y masa; revise instrucciones del fabricante. Reemplace los cuatro valores fijos del sketch manteniendo nombres y unidades. No conecte bombas ni sondas desnudas al GPIO sin la interfaz correspondiente.

06 / Comprender el backend

Persistencia NoSQL, API y motor de reglas

La versión base adopta dos colecciones en irrigation para reducir inconsistencias: measurements (lecturas, reglas aplicadas, estados y cambios de estado en un único documento atómico) y alarm_rules (configuración vigente por equipo). El estado actual se deriva de la última medición y los eventos se consultan desde documentos históricos. La propuesta original de colecciones independientes alarm_events, alarm_state y devices puede incorporarse al escalar; aquí no se necesitan transacciones multicolección.

{
  "_id": "uno-r4-001:lab-001:1024",
  "device_id": "uno-r4-001",
  "boot_id": "lab-001",
  "seq": 1024,
  "timestamp": "BSON Date (UTC)",
  "soil_moisture": 20.0,
  "temperature": 25.0,
  "soil_ec": 2.8,
  "water_ph": 6.7,
  "states": {"soil_moisture":"LOW", "temperature":"NORMAL", "soil_ec":"HIGH", "water_ph":"NORMAL"},
  "events": ["documentos de cambios de estado"],
  "rules": {"...":"reglas aplicadas a esta muestra"}
}

El índice compuesto device_id + timestamp acelera consultas por nodo e intervalo; el índice único implícito de _id impide duplicados. El usuario de aplicación tiene readWrite solo para la base de datos irrigation. Los scripts de inicialización MongoDB se ejecutan únicamente al crear un volumen vacío: editar las contraseñas en .env después de inicializar no cambia usuarios existentes.

6.1 Consultar la base sin exponerla

El siguiente comando es idéntico en los tres SO. Abre mongosh en el contenedor y pide la contraseña del usuario iotapp (APP_DB_PASSWORD en .env):

6.2 Estados e histéresis

VariableMín.Máx.HistéresisDecisión simulada
Humedad %25653Evaluar inicio/detención de riego
Temperatura °C15301Revisar frío/estrés térmico
EC mS/cm0,52,50,1Revisar nutrientes/salinidad
pH del agua5,57,50,2Revisar acidez/alcalinidad

Son umbrales ilustrativos, no recomendaciones agronómicas. Si x < L se activa LOW; si x > U se activa HIGH. Desde LOW se recupera NORMAL cuando x ≥ L+h, y desde HIGH cuando x ≤ U−h, salvo salto directo al umbral opuesto. Se exige L < U y 0 ≤ h ≤ (U−L)/2. Si la regla está deshabilitada, se usa DISABLED. Un evento solo se genera al cambiar de estado. Las reglas nuevas se evalúan con la próxima muestra, no retroactivamente. Las líneas del gráfico son las reglas actuales, no necesariamente las reglas vigentes en cada medición histórica.

Ejemplo: con L=25 y h=3, la secuencia 30, 24, 25, 27, 28 produce NORMAL, LOW, LOW, LOW, NORMAL. Se usa un solo worker porque ordena las evaluaciones según recepción; varias instancias requerirían coordinación. El worker utiliza sesión MQTT persistente y ACK de QoS 1 después de insertar. En caso de fallo de BD reinicia sin ACK; el broker puede reenviar según el estado de sesión. No garantiza no perder muestras si falla el broker, se agota su cola, se pierde su volumen o el Arduino no reintenta con persistencia. Es un laboratorio, no un sistema de seguridad funcional.

1 · Emitir certificado público (Ubuntu remoto)

COMPOSE_FILE=compose.yaml:compose.tls.yaml

sudo docker compose config --quiet

3 · Configurar Arduino

Abra arduino/uno_r4_tls/uno_r4_tls.ino. Utiliza WiFiSSLClient, puerto 8883 y nombre DNS, no IP. Complete SSID, contraseña Wi-Fi, MQTT_PASSWORD y nuevo BOOT_ID. 12 / Operación y costos

Persistencia, respaldos y mantenimiento

12.1 Operar sin borrar información

En DROPLET, desde ~/irrigation-droplet:

sudo docker compose ps
sudo docker compose logs --tail=50
sudo docker compose logs -f mqtt-worker
sudo docker stats --no-stream
sudo docker system df

Ctrl+C sale del seguimiento de logs. Los servicios tienen restart: unless-stopped y el Docker Engine queda habilitado para arrancar en Ubuntu. Después de un reinicio normal, los contenedores que estaban activos deberían volver; si los detuvo explícitamente, levántelos con up -d. Compruebe /health y el túnel al reconectar.

sudo docker compose stop
sudo docker compose up -d --wait --wait-timeout 180

Se utilizan dos volúmenes Docker nombrados, mongo_data y mqtt_data, almacenados en el SSD virtual del Droplet. Conservar el nombre del proyecto/directorio es importante. Reiniciar o docker compose down sin -v conserva los volúmenes. Eliminar el Droplet elimina su disco; los datos no son independientes como el EBS del diseño anterior. Los logs tienen rotación configurada en Compose.

No ejecute docker compose down -v, docker volume prune ni elimine archivos de /var/lib/docker para solucionar una falla. Son acciones potencialmente destructivas.

12.2 Respaldo lógico de MongoDB

Detenga el simulador y desconecte temporalmente el Arduino. El script detiene dashboard y worker para que no escriban durante el volcado, ejecuta mongodump y los reinicia al salir; Mosquitto queda activo y puede encolar mensajes QoS 1, sujeto a límites. El archivo contiene mediciones y reglas, no la configuración de usuarios ni la sesión MQTT.

cd ~/irrigation-droplet
bash droplet/backup.sh
ls -lh backups

En el PC descargue el archivo (reemplace NOMBRE por el mostrado; mantenga copia fuera del Droplet):

scp iot@IP_DROPLET:~/irrigation-droplet/backups/NOMBRE.archive.gz .

Guarde por separado .env original, claves/certificados necesarios y versión del código de forma cifrada y con acceso restringido. No los suba a GitHub. Para una copia integral, puede contratar backups/snapshots de DigitalOcean: detenga los servicios y siga la recomendación de consistencia del proveedor. El costo y retención son adicionales.

Restauración en un Droplet nuevo de prueba

Prepare una instalación nueva con su propio .env y las mismas versiones compatibles, sin conectar Arduino ni ejecutar simulador; transfiera el archivo de backup. En la carpeta del proyecto, detenga escritores y restaure la base irrigation. Ejemplo con archivo en backups/restore.archive.gz:

No use --drop sobre una base activa. Este ejemplo supone una base nueva vacía (solo índices iniciales); confirme que no haya documentos previos. Compare conteos, muestras, reglas y estados en el dashboard. La prueba de recuperación no fue ejecutada aquí; debe comprobarse antes de confiar en un backup.

12.3 Actualizar una versión

Con respaldo previo, modifique el código en el mismo proyecto o copie únicamente archivos revisados (no .env). Construya una etiqueta nueva, cambie APP_IMAGE en .env y vuelva a desplegar. Ejemplo:

sudo docker build -t irrigation:1.0.1 .
nano .env

Cambie solo APP_IMAGE a irrigation:1.0.1; después:

sudo docker compose up -d --wait --wait-timeout 180

En caso de fallo, vuelva a la etiqueta anterior si los esquemas siguen siendo compatibles. No actualice versiones mayores de MongoDB sin revisar el procedimiento oficial de migración. No cambie hashes de contraseñas en .env sin cambiar las credenciales de la base existente.

12.4 Costos y cierre

DigitalOcean cobra por el Droplet creado, incluso apagado. Los planes Basic tienen tope mensual y se facturan según tiempo (consulte precios vigentes); el firewall cloud no tiene costo adicional. Backups, snapshots, almacenamiento extra, IP reservada sin asignar, exceso de transferencia y dominio pueden sumar costos. Eliminar el Droplet es irreversible: primero descargue y pruebe sus respaldos.

  1. En la consola, confirme el Droplet correcto, respaldos y política de datos de la institución.
  2. Cuando ya no lo necesite, Actions → Destroy. No borre recursos compartidos.
  3. Revise backups, snapshots, volúmenes y Reserved IPs que puedan seguir generando cargos. Verifique Billing.

No hay alta disponibilidad: la caída o pérdida del Droplet interrumpe broker, base y dashboard. La solución cumple un propósito experimental y no garantiza entrega sin pérdidas ni operación segura de actuadores.

# Smart Irrigation · DigitalOcean
Guía HTML complementaria: `guia-iot-digitalocean.html`.

- Mosquitto, MongoDB, worker Python y Flask/Gunicorn: cuatro servicios, tres imágenes.
- Local (red aislada): copie `.env.example` a `.env`, `docker build -t irrigation:1.0.0 .`, `docker compose up -d --wait --wait-timeout 180`.
- Droplet nuevo Ubuntu 24.04: `sudo bash droplet/install-docker.sh`, `bash droplet/init-env.sh`, `sudo docker build -t irrigation:1.0.0 .`, `sudo docker compose up -d --wait --wait-timeout 180`, `bash droplet/check.sh`.
- Dashboard no autenticado, solo loopback 8080 y túnel SSH. MQTT 1883 loopback; TLS 8883 con `compose.tls.yaml` únicamente tras configurar certificados y firewall. Nunca exponga MongoDB.
- Verifique los pasos de la guía antes de conectar hardware. Los sketches son telemetría sintética, no drivers de sensores.
- No publique `.env`, certificados, archivos de respaldo, contraseñas o claves SSH.
- No ejecute `docker compose down -v` sobre datos que desea conservar.
- Pruebas unitarias: `python -m unittest discover -s tests` (Python instalado; no necesita dependencias externas).
- La guía documenta límites de las pruebas efectuadas y las pendientes de Docker/Arduino/DigitalOcean.

import math

DEFAULTS = {
    'soil_moisture': {'min': 25, 'max': 65, 'h': 3, 'enabled': True},
    'temperature': {'min': 15, 'max': 30, 'h': 1, 'enabled': True},
    'soil_ec': {'min': 0.5, 'max': 2.5, 'h': 0.1, 'enabled': True},
    'water_ph': {'min': 5.5, 'max': 7.5, 'h': 0.2, 'enabled': True},
}
RANGES = {'soil_moisture': (0,100), 'temperature': (-40,125), 'soil_ec': (0,100), 'water_ph': (0,14)}
DECISIONS = {
 'soil_moisture': ('Evaluar inicio de riego', 'Evaluar detención de riego'),
 'temperature': ('Revisar temperatura baja', 'Revisar estrés térmico'),
 'soil_ec': ('Revisar nutrientes y calibración', 'Revisar salinidad'),
 'water_ph': ('Revisar acidez', 'Revisar alcalinidad'),
}

def number(v):
    if isinstance(v, bool) or not isinstance(v, (int,float)) or not math.isfinite(v):
        raise ValueError('Se requiere número finito')
    return float(v)

def validate_rules(rules):
    if not isinstance(rules, dict) or set(rules) != set(DEFAULTS):
        raise ValueError('Se requieren cuatro reglas')
    result = {}
    for k, r in rules.items():
        if not isinstance(r,dict) or set(r) != {'min','max','h','enabled'} or not isinstance(r['enabled'],bool):
            raise ValueError('Regla inválida: '+k)
        lo, hi, h = (number(r[n]) for n in ('min','max','h'))
        a,b=RANGES[k]
        if not (a <= lo < hi <= b and 0 <= h <= (hi-lo)/2):
            raise ValueError('Límites o histéresis inválidos: '+k)
        result[k] = {'min':lo,'max':hi,'h':h,'enabled':r['enabled']}
    return result

def state(value, rule, previous='NORMAL'):
    if not rule['enabled']: return 'DISABLED'
    lo,hi,h=rule['min'],rule['max'],rule['h']
    if value < lo: return 'LOW'
    if value > hi: return 'HIGH'
    if previous == 'LOW' and value < lo+h: return 'LOW'
    if previous == 'HIGH' and value > hi-h: return 'HIGH'
    return 'NORMAL'

def evaluate(values, rules, previous):
    states, events = {}, []
    for k,v in values.items():
        before=previous.get(k,'NORMAL')
        after=state(v,rules[k],before)
        states[k]=after
        if after != before:
            decision = DECISIONS[k][0 if after=='LOW' else 1] if after in ('LOW','HIGH') else ('Recuperación del rango' if after=='NORMAL' else 'Alarma deshabilitada')
            events.append({'sensor':k,'from':before,'to':after,'value':v,'decision':decision})
    return states,events

import os,json,logging,re
from datetime import datetime,timezone
import paho.mqtt.client as mqtt
from pymongo.errors import DuplicateKeyError
from alarm_engine import RANGES,number,evaluate
from database import db,rules_for
logging.basicConfig(level=logging.INFO,format='%(asctime)s %(levelname)s %(message)s')

def parse(topic,payload):
    p=topic.split('/')
    if len(p)!=3 or p[0]!='irrigation' or p[2]!='telemetry' or not re.fullmatch(r'[A-Za-z0-9_-]{1,64}',p[1]): raise ValueError('topic')
    if len(payload)>4096: raise ValueError('payload demasiado grande')
    d=json.loads(payload)
    if not isinstance(d,dict) or d.get('device_id')!=p[1]: raise ValueError('device_id')
    boot=d.get('boot_id'); seq=d.get('seq')
    if not isinstance(boot,str) or not re.fullmatch(r'[A-Za-z0-9_-]{1,64}',boot) or type(seq) is not int or not 0<=seq<2**63: raise ValueError('identificador')
    vals={}
    for k,(lo,hi) in RANGES.items():
        v=number(d.get(k))
        if not lo<=v<=hi: raise ValueError(k)
        vals[k]=v
    return p[1],boot,seq,vals

def on_connect(c,u,f,rc,props):
    if rc==0:
        c.subscribe('irrigation/+/telemetry',qos=1)
        logging.info('Conectado; suscripción solicitada')
    else: logging.error('MQTT: %s',rc)

def on_subscribe(c,u,mid,reason_codes,properties):
    if reason_codes and all(not rc.is_failure for rc in reason_codes):
        logging.info('Suscripción MQTT confirmada')
    else: logging.error('Suscripción MQTT rechazada: %s',reason_codes)

def on_message(c,u,m):
    try:
        device,boot,seq,vals=parse(m.topic,m.payload)
    except (ValueError,TypeError,OverflowError):
        logging.warning('Mensaje inválido descartado')
        if m.qos: c.ack(m.mid,m.qos)
        return
    key=f'{device}:{boot}:{seq}'
    try:
        if not db.measurements.find_one({'_id':key},{'_id':1}):
            prev=db.measurements.find_one({'device_id':device},sort=[('timestamp',-1),('_id',-1)]) or {}
            rules=rules_for(device)
            states,events=evaluate(vals,rules,prev.get('states',{}))
            db.measurements.insert_one({'_id':key,'device_id':device,'boot_id':boot,'seq':seq,'timestamp':datetime.now(timezone.utc),**vals,'states':states,'events':events,'rules':rules})
            logging.info('Guardado %s %s',key,states)
    except DuplicateKeyError: pass
    except Exception:
        logging.exception('Fallo de persistencia; reiniciar sin ACK')
        # El proceso sale; Compose lo reinicia. Sesión MQTT persistente.
        os._exit(1)
    if m.qos: c.ack(m.mid,m.qos)

if __name__=='__main__':
    c=mqtt.Client(mqtt.CallbackAPIVersion.VERSION2,client_id='irrigation-worker',clean_session=False,manual_ack=True)
    c.username_pw_set(os.environ['MQTT_USER'],os.environ['MQTT_PASSWORD'])
    c.on_connect=on_connect; c.on_subscribe=on_subscribe; c.on_message=on_message
    c.reconnect_delay_set(1,30)
    c.connect_async('mosquitto',1883,60)
    c.loop_forever(retry_first_connection=True)
