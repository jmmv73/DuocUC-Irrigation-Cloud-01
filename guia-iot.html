00 / Punto de partida

Cómo trabajar con esta guía

Este laboratorio entrega una aplicación Python de referencia, Dockerfile, Compose, simulador, configuración de Mosquitto y MongoDB, scripts de AWS y un sketch Arduino de telemetría sintética. No necesita instalar Python ni MongoDB en el computador: se ejecutarán dentro de los contenedores.

ZIP junto a la guía

El primer botón utiliza el ZIP incorporado en este HTML, incluso sin conexión. El segundo funciona cuando ambos archivos están en el mismo directorio o sitio web. Las imágenes Docker y los servicios AWS sí requieren Internet.

Parte A · LocalInstalar, construir, simular y verificar.
Parte B · EC2Publicar la imagen y verificar una instancia.
Parte C · AMIAutomatizar instalación y prueba de integración.
Alcance y certeza. Se comprobaron cinco pruebas unitarias Python del motor de alarmas, sintaxis Python, JavaScript, shell y lectura YAML. No se ejecutó Docker, Arduino ni una cuenta AWS durante la elaboración. Por tanto, es código de referencia revisado, no una aplicación certificada ni una guía validada experimentalmente extremo a extremo. Cada fase incluye un control de aceptación: no avance si falla. Las versiones de imágenes base por familia (MongoDB 8.0, Mosquitto 2, Python 3.12) y paquetes de sistema pueden recibir actualizaciones. Los pasos de consola AWS pueden cambiar de nombre.

Seleccione su sistema operativo

Esto solo filtra los bloques de instrucciones específicos. Los bloques universales y los comandos de EC2 Linux siempre se muestran.

Convenciones: copie un bloque completo cuando se indique, sin copiar un símbolo de prompt. Los comandos con REEMPLAZAR, BUCKET o direcciones de ejemplo deben editarse antes de ejecutar. Abra el terminal en la carpeta donde está Dockerfile. Deténgase ante un error; no ejecute comandos de borrado para intentar repararlo.

Recomendación local: computador de 64 bits, 8 GB de RAM o más, 10 GB libres como punto de partida, conexión a Internet y permisos para instalar software. Para Windows utilice un sistema compatible con Docker Desktop, virtualización habilitada y WSL2. En Linux se detalla Ubuntu 24.04 LTS; para otras distribuciones utilice la documentación oficial de su gestor de paquetes.

MongoDB es representativa de sistemas de documentos reales y permite consultas, índices y persistencia histórica.   2. En PowerShell como administrador, compruebe WSL. Si no está instalado, utilice el comando indicado y reinicie si Windows lo solicita.
wsl --status

03 / Primer sistema funcionando

Construir la imagen y levantar los servicios

3.1 Extraer el proyecto

Descargue el ZIP de la sección 00. Cree una carpeta llamada irrigation-lab, extraiga todo dentro de ella. El ZIP contiene los archivos directamente, sin una carpeta raíz. No arrastre únicamente los archivos visibles: incluya .env.example, .dockerignore y .gitignore. En macOS Finder se pueden mostrar ocultos con Cmd+Shift+.

macOS / Linux

Si descargó a Downloads (o Descargas), ajuste la ruta real. Alternativamente, abra una terminal en la carpeta extraída.

cd ~/Downloads/irrigation-lab
ls -la
cp .env.example .env

Windows / PowerShell

Set-Location "$HOME\Downloads\irrigation-lab"
Get-ChildItem -Force
Copy-Item .env.example .env

Debe encontrar Dockerfile, compose.yaml, app/, mosquitto/, mongo-init/ y aws/. Las contraseñas de .env.example son exclusivamente para pruebas locales aisladas. Nunca use esas contraseñas públicamente ni suba .env a GitHub. Mantenga MQTT_USER=worker pues coincide con la ACL.

3.2 Aprender Docker construyendo

Ejecute desde la carpeta del proyecto en cualquier SO:

docker build -t irrigation:1.0.0 .
docker image ls irrigation

FROM utiliza Python 3.12; COPY incorpora el código; RUN instala dependencias y crea un usuario sin privilegios; CMD ejecuta Gunicorn. Se utiliza otra orden para el worker dentro de Compose. El punto final selecciona el directorio como contexto de build. En el primer build se descargan capas y paquetes. El Dockerfile y las dependencias directas están disponibles en la sección 15.

3.3 Validar Compose y arrancar

docker compose config --quiet
docker compose up -d --wait --wait-timeout 180
docker compose ps
docker compose logs --tail=30 mqtt-worker

Compose descarga las imágenes públicas de Mosquitto y MongoDB si no existen. -d mantiene servicios en segundo plano. --wait comprueba sus estados y health checks; el worker no tiene health check propio, así que revise su log. En docker compose ps espere cuatro servicios en ejecución, MongoDB, broker y dashboard saludables. El worker deberá escribir “Conectado; suscripción solicitada”. El dashboard puede indicar que todavía no hay mediciones.

Abra http://localhost:8080 y, en otra pestaña, http://localhost:8080/health. El segundo endpoint debe responder {"ok":true}.

Control 03: cuatro servicios activos y página de salud correcta. Si aparece error de MongoDB o del puerto, vaya a la sección 13. No use docker compose down -v para solucionar fallas: borra los datos.

04 / Validación con datos sintéticos

Dashboard, histórico y decisiones

No conecte aún el Arduino: primero aislemos los problemas de software. El simulador ejecuta Python en un contenedor temporal de la misma imagen. El mensaje determinista de prueba es humedad 20 %, temperatura 25 °C, EC 2,8 mS/cm y pH 6,7.

docker compose run --rm simulator python simulator.py --once

Conductividad2.80 mS/cmHIGH · revisar salinidad
pH agua6.70 pHNORMAL

Representación de la salida esperada con reglas iniciales intactas. No es una lectura real del Arduino.

Refresque el dashboard; la página consulta cada cinco segundos. Verifique los estados anteriores y una decisión para humedad y conductividad. El histórico genera cuatro gráficas SVG, con tiempos reales de recepción, límites actuales y hasta 5000 muestras por consulta. La base conserva todos los documentos salvo que se configure retención.

4.1 Flujo continuo

docker compose run --rm simulator python simulator.py --interval 5

Deje ese terminal abierto; se generarán valores cada cinco segundos. Para terminarlo utilice Ctrl+C. Las cuatro tarjetas se actualizan y las gráficas muestran el histórico. No ejecute simultáneamente el simulador y el Arduino con el mismo ID de dispositivo, pues mezclaría ambas fuentes.

4.2 Cambiar alarmas

  1. Detenga el simulador continuo. En el dashboard ajuste humedad mínima de 25 a 10 y mantenga máximo 65 e histéresis 3. Pulse Guardar reglas.
  2. Vuelva a publicar la muestra determinista. Humedad 20 debe pasar de LOW a NORMAL si el último estado era LOW, o mantenerse NORMAL.
  3. Cambie el mínimo a 25, publique otra muestra y debe observar LOW.
  4. Pruebe mínimo mayor al máximo: el backend rechaza la regla y conserva la anterior.
  5. Deshabilite una variable, publique y compruebe DISABLED. Restituya valores apropiados para el ejercicio.

4.3 Deduplicación y persistencia

docker compose run --rm simulator python simulator.py --once --boot duplicate-test
docker compose run --rm simulator python simulator.py --once --boot duplicate-test

El mismo boot_id y secuencia, siempre cero para --once, identifican ambas publicaciones como una medición. El histórico debe tener solo un documento adicional respecto del conteo anterior (detenga otras fuentes y use idéntica ventana temporal). Repita con otro identificador si ya había usado duplicate-test.

docker compose down
docker compose up -d --wait --wait-timeout 180

Consulte el histórico y las reglas: deben persistir. Si no llegan muestras durante 90 segundos, se indica “Sin datos recientes”, que no es necesariamente una prueba de que el dispositivo esté apagado. No implica la desaparición de las mediciones previas.

Control 04: las cuatro tarjetas, gráficas, modificación de reglas, eventos, deduplicación y persistencia funcionan. Registre capturas y el resultado de cada prueba antes de conectar hardware.
05 / Integración física

Arduino UNO R4 WiFi y MQTT

Use primero el sketch arduino/uno_r4_demo/uno_r4_demo.ino. Publica valores fijos para comprobar red y protocolo; no mide sensores. La placa UNO R4 WiFi incluye conectividad mediante un módulo ESP32 y usa la librería WiFiS3. No confundir con Arduino UNO R4 Minima.

5.1 Permitir acceso desde la red local

Arduino y PC deben estar en la misma red privada, sin aislamiento Wi-Fi de clientes. Detenga el simulador. En el archivo .env, cambie MQTT_BIND=127.0.0.1 por MQTT_BIND=0.0.0.0 (o la IP LAN concreta si Docker en ese SO permite enlazarla). Mantenga el dashboard en localhost. Reinicie el broker:

docker compose up -d --wait --wait-timeout 180

macOS · IP de la interfaz Wi-Fi

networksetup -listallhardwareports
ipconfig getifaddr en0

Si Wi-Fi corresponde a otra interfaz, reemplace en0. Revise Ajustes → Red → Wi-Fi → Detalles. Permita Docker en el firewall del sistema solo en la red confiable si aparece una solicitud.

Linux · IP del equipo

ip -4 addr

Identifique la interfaz Wi-Fi/Ethernet conectada al Arduino. Docker publica puertos usando reglas propias de firewall; no confíe únicamente en UFW para aislar un puerto publicado. Use una red de laboratorio aislada, sin redirección de puertos del router; para restricciones avanzadas revise las reglas DOCKER-USER y la documentación de firewall de Docker.

Windows · IP del adaptador físico

ipconfig

Seleccione la IPv4 del adaptador Wi-Fi/Ethernet, no la del adaptador virtual WSL. En Windows Defender Firewall permita TCP 1883 en perfil privado y alcance de subred local si hace falta. No habilite perfiles públicos.

MQTT en 1883 no cifra usuario, contraseña ni telemetría. Úselo únicamente en red confiable de laboratorio. No abra el puerto 1883 en el router o Security Group de AWS. Si no puede garantizar el aislamiento, omita esta prueba y use TLS.

5.2 Cargar sketch

  1. Conecte el UNO R4 WiFi por USB. Arduino IDE → Boards Manager → instale Arduino UNO R4 Boards. Library Manager → instale ArduinoMqttClient. WiFiS3 forma parte del soporte de la placa.
  2. Seleccione Arduino UNO R4 WiFi y el puerto USB correspondiente. Abra el sketch incluido.
  3. Edite SSID, WIFI_PASSWORD, BROKER (IP del computador), MQTT_PASSWORD (valor de ARDUINO_MQTT_PASSWORD en .env). Use un BOOT_ID distinto para cada reinicio de ensayo, pues la secuencia se reinicia. Esta decisión simplifica el sketch: en una versión real genere un ID de sesión único automáticamente, mediante persistencia o una fuente adecuada de aleatoriedad.
  4. Pulse Verify y Upload. Abra Serial Monitor a 115200 baud. Espere 30 s. Observe el JSON impreso tras recibir PUBACK del broker y verifique el dashboard.

5.4 Sustituir datos sintéticos por lecturas reales

No es correcto asignar pines o ecuaciones universalmente: no se especificaron modelos de sensores. Obtenga datasheets, verifique tensiones (UNO R4 WiFi usa lógica de 5 V), corriente, rango de salida, referencia ADC y aislamiento. Con humedad capacitiva, determine niveles de calibración seco/húmedo; para EC especifique unidad y método, compensación de temperatura y calibración; para pH utilice soluciones buffer y acondicionamiento de alta impedancia adecuados. La humedad expresada en porcentaje de calibración no equivale automáticamente a contenido volumétrico de agua. Muchos módulos EC y pH pueden interferir si comparten el medio y masa; revise instrucciones del fabricante. Reemplace los cuatro valores fijos del sketch manteniendo nombres y unidades. No conecte bombas ni sondas desnudas al GPIO sin la interfaz correspondiente.

06 / Comprender el backend

Persistencia NoSQL, API y motor de reglas

La versión base adopta dos colecciones en irrigation para reducir inconsistencias: measurements (lecturas, reglas aplicadas, estados y cambios de estado en un único documento atómico) y alarm_rules (configuración vigente por equipo). El estado actual se deriva de la última medición y los eventos se consultan desde documentos históricos. La propuesta original de colecciones independientes alarm_events, alarm_state y devices puede incorporarse al escalar; aquí no se necesitan transacciones multicolección.

{
  "_id": "uno-r4-001:lab-001:1024",
  "device_id": "uno-r4-001",
  "boot_id": "lab-001",
  "seq": 1024,
  "timestamp": "BSON Date (UTC)",
  "soil_moisture": 20.0,
  "temperature": 25.0,
  "soil_ec": 2.8,
  "water_ph": 6.7,
  "states": {"soil_moisture":"LOW", "temperature":"NORMAL", "soil_ec":"HIGH", "water_ph":"NORMAL"},
  "events": ["documentos de cambios de estado"],
  "rules": {"...":"reglas aplicadas a esta muestra"}
}

El índice compuesto device_id + timestamp acelera consultas por nodo e intervalo; el índice único implícito de _id impide duplicados. El usuario de aplicación tiene readWrite solo para la base de datos irrigation. Los scripts de inicialización MongoDB se ejecutan únicamente al crear un volumen vacío: editar las contraseñas en .env después de inicializar no cambia usuarios existentes.

6.1 Consultar la base sin exponerla

El siguiente comando es idéntico en los tres SO. Abre mongosh en el contenedor y pide la contraseña del usuario iotapp (APP_DB_PASSWORD en .env):

6.2 Estados e histéresis

VariableMín.Máx.HistéresisDecisión simulada
Humedad %25653Evaluar inicio/detención de riego
Temperatura °C15301Revisar frío/estrés térmico
EC mS/cm0,52,50,1Revisar nutrientes/salinidad
pH del agua5,57,50,2Revisar acidez/alcalinidad

Son umbrales ilustrativos, no recomendaciones agronómicas. Si x < L se activa LOW; si x > U se activa HIGH. Desde LOW se recupera NORMAL cuando x ≥ L+h, y desde HIGH cuando x ≤ U−h, salvo salto directo al umbral opuesto. Se exige L < U y 0 ≤ h ≤ (U−L)/2. Si la regla está deshabilitada, se usa DISABLED. Un evento solo se genera al cambiar de estado. Las reglas nuevas se evalúan con la próxima muestra, no retroactivamente. Las líneas del gráfico son las reglas actuales, no necesariamente las reglas vigentes en cada medición histórica.

Ejemplo: con L=25 y h=3, la secuencia 30, 24, 25, 27, 28 produce NORMAL, LOW, LOW, LOW, NORMAL. Se usa un solo worker porque ordena las evaluaciones según recepción; varias instancias requerirían coordinación. El worker utiliza sesión MQTT persistente y ACK de QoS 1 después de insertar. En caso de fallo de BD reinicia sin ACK; el broker puede reenviar según el estado de sesión. No garantiza no perder muestras si falla el broker, se agota su cola, se pierde su volumen o el Arduino no reintenta con persistencia. Es un laboratorio, no un sistema de seguridad funcional.

07 / Preparar el entorno Cloud

Cuenta AWS, permisos, red y presupuesto

Realice esta parte solo después del control 05 (o después del control 04 si no hay Arduino). Mantenga la región constante. Usaremos us-east-1 como ejemplo, no como exigencia; se puede elegir otra región autorizada cambiando todos los comandos y referencias correspondientes.

  1. Ingrese a la consola AWS con su usuario o rol institucional, no root. Active MFA cuando corresponda. En AWS Academy/Learner Lab, confirme antes que ECR, S3, EC2 Image Builder e IAM estén permitidos. Algunos entornos docentes impiden crear roles o pipelines; el administrador debe habilitarlos. No intente eludir restricciones.
  2. Configure un presupuesto y alertas de facturación en AWS Budgets. Las alertas no son un límite duro ni detienen automáticamente todos los recursos.
  3. Identifique una VPC y subred pública con ruta al Internet Gateway. Para una configuración inicial sencilla, use la VPC predeterminada si existe y está autorizada. Habilite IP IPv4 pública para instancias de construcción y operación si no tiene otra salida a Internet. Para una VPC privada hacen falta conectividad saliente/NAT o endpoints adecuados. No use una VPC sin DNS y rutas apropiadas.
  4. Prepare dos Security Groups. Para construcción, sin reglas entrantes; salida HTTPS y acceso necesario a repositorios Ubuntu, Docker Hub, AWS y DNS (en un lab simple, salida predeterminada). Construir la AMI con EC2 Image Builder

↓ docker buildx --push

↓ build → validate → snapshot → test

Image Builder crea una AMI; no recibe un Dockerfile para ejecutar contenedores por sí solo. También admite recipes de contenedores, pero aquí la imagen Python ya se creó en la estación local. La AMI incluye Docker Compose, las imágenes descargadas, configuración y servicio systemd. Las credenciales y datos se crean después del lanzamiento. 10.1 Crear componente personalizado

  1. En la misma región, navegue a EC2 Image Builder → Components → Create component.
  2. Seleccione sistema Linux y tipo Build (el documento incluye build, validate y test), nombre SmartIrrigationAMI, versión 1.0.0.
  3. En definición del componente, pegue o cargue el contenido completo de aws/image-builder.yaml del ZIP. También está al final de esta guía. Cree el componente.
  4. El documento declara dos parámetros: DeploymentUri (S3 URI real del ZIP) y AppImage (URI real de ECR con versión). Sustituya los valores de ejemplo al crear la recipe o, antes de crear el componente, edite sus defaults. No use secretos como parámetros.

AWSTOE ejecuta comandos Linux en las instancias de Image Builder con permisos elevados. Build instala software y descarga las imágenes; validate verifica los artefactos; test arranca los servicios con credenciales locales desechables, publica una muestra MQTT y verifica en la API los estados LOW/HIGH. El script de test elimina únicamente sus volúmenes temporales. La AMI no contiene esa información de prueba. Si falla el smoke test no se debe distribuir como resultado válido.

10.2 Crear Image Recipe

  1. Image Builder → Image recipes → Create image recipe. Nombre smart-irrigation-recipe, versión 1.0.0.

10.3 Infrastructure configuration

  1. Image Builder → Infrastructure configurations → Create. Nombre smart-irrigation-build-infra.
  2. Instance profile: SmartIrrigationImageBuilderRole. Tipo de instancia t3.medium (puede usar t3.large si falla por memoria durante build/test).
  3. VPC/subred con conectividad saliente a AWS, Ubuntu y Docker Hub. Si usa subred pública, verifique auto-assign public IP en la subred; no basta una ruta a Internet Gateway si la instancia no tiene IP pública. No requiera puertos entrantes. Seleccione el Security Group de construcción.

Si mantiene instancias, recuerde terminarlas. Puede habilitar logs S3/CloudWatch con los permisos necesarios; si no, revise los logs del pipeline en la consola.

10.4 Distribution configuration y pipeline

  1. Image Builder → Distribution configurations → Create. Nombre smart-irrigation-distribution. AMI en la región actual y acceso privado. Nombre con marca temporal usando la expresión soportada, por ejemplo Smart-Irrigation-AMI-{{imagebuilder:buildDate}}.
  2. Image pipelines → Create image pipeline. Nombre smart-irrigation-pipeline, manual (sin schedule periódico), recipe anterior, infrastructure y distribution configuration anteriores. Mantenga pruebas habilitadas. Puede usar el workflow predeterminado y rol vinculado al servicio; no confunda ese rol con el instance profile de las instancias.

  4. Image Builder → Images → seleccione ejecución y revise etapas, mensajes y salida. Si falla, identifique paso exacto; no ignore un fallo en test. Si necesita corregir componente/recipe cree una nueva versión 1.0.1 (no reescriba una versión publicada).

11 / Conectar el Arduino desde Internet

MQTT seguro con TLS en el puerto 8883

La prueba en EC2 con simulador y dashboard por SSH no requiere puertos públicos adicionales. Para el hardware físico sí se necesita un camino seguro. Esta etapa es avanzada: requiere dominio/DNS bajo su control, una IP pública estable, certificado de confianza y verificación del soporte TLS de la placa. Si no dispone de esos recursos, mantenga la práctica en simulación cloud o utilice una VPN administrada por su institución. No use 1883 público como atajo.

11.1 Certificado

  1. Asocie una Elastic IP o una IP estable autorizada, con costos asociados, a EC2. Cree un registro DNS A como mqtt.ejemplo.cl hacia esta IP (nombre real bajo su control).
  2. Obtenga un certificado público con una CA compatible con el firmware de Arduino. Ejemplo con Certbot DNS-01 manual en Ubuntu. No necesita abrir 80 ni 443 para DNS-01; requiere permisos sobre la zona DNS. Cumpla las instrucciones de Certbot y espere propagación antes de confirmar.
sudo apt-get update
sudo apt-get install -y certbot
sudo certbot certonly --manual --preferred-challenges dns -d mqtt.ejemplo.cl

Reemplace el dominio real. Si usa una CA corporativa, siga su procedimiento. Copie los certificados al directorio que montará el broker; no copie enlaces simbólicos sin su contenido y no haga pública la clave privada. En EC2:

cd /opt/smart-irrigation
sudo mkdir -p certs
sudo cp -L /etc/letsencrypt/live/mqtt.ejemplo.cl/fullchain.pem certs/fullchain.pem
sudo cp -L /etc/letsencrypt/live/mqtt.ejemplo.cl/privkey.pem certs/privkey.pem
GID=$(sudo docker run --rm --entrypoint id eclipse-mosquitto:2 -g mosquitto)
sudo chown root:$GID certs certs/fullchain.pem certs/privkey.pem
sudo chmod 750 certs
sudo chmod 644 certs/fullchain.pem
sudo chmod 640 certs/privkey.pem

Edite sudo nano /opt/smart-irrigation/.env. Cambie únicamente COMPOSE_FILE por COMPOSE_FILE=compose.yaml:compose.aws.yaml:compose.tls.yaml. Mantenga MQTT_BIND=127.0.0.1: 1883 seguirá enlazado solo a loopback y las conexiones del worker se mantienen internas. El override activa un listener TLS y publica 8883. Reinicie:

sudo systemctl restart irrigation.service
sudo docker compose ps
sudo docker compose logs --tail=30 mosquitto

11.2 Security Group y verificación

En el Security Group de operación agregue Custom TCP 8883 con origen IP pública de salida del laboratorio/Arduino en CIDR (por ejemplo una sola IP /32 cuando sea estable). No es la IP LAN 192.168.x.x. Mantenga 1883, 8080 y 27017 sin inbound. Si varios lugares necesitan acceso, liste sus redes autorizadas. No abra a todo Internet salvo que exista una justificación y controles reforzados.

Desde un equipo con OpenSSL, en la red autorizada, valide el handshake y el nombre:

openssl s_client -connect mqtt.ejemplo.cl:8883 -servername mqtt.ejemplo.cl -verify_hostname mqtt.ejemplo.cl -verify_return_error

Debe aparecer verificación satisfactoria (Verify return code: 0). Ctrl+C para salir. Si OpenSSL no está disponible en Windows, puede usar WSL con OpenSSL instalado o un cliente MQTT gráfico de confianza que valide TLS, sin aceptar certificados inválidos. La verificación TLS no sustituye una prueba de publicación autenticada; pruebe con un cliente MQTT con TLS, tópico autorizado y usuario/contraseña correctos. No use opciones insecure.

El certificado de ejemplo DNS-01 manual no se renueva automáticamente sin automatizar el challenge. Controle vencimiento, repita la emisión/renovación según el proveedor, recopie los archivos con permisos correctos y reinicie el broker mediante systemd. Para operación estable configure renovación automatizada con proveedor DNS autorizado y un deploy hook. Revise también rotación de credenciales.

11.3 Cambios al sketch

Use el hostname DNS que coincide con el certificado, cambie WiFiClient wifi; por WiFiSSLClient wifi; y mqtt.connect(BROKER,1883) por puerto 8883. La contraseña del Arduino es la generada por bootstrap en la variable ARDUINO_MQTT_PASSWORD de .env en EC2. Recupérela de forma privada, no en pantallas compartidas. No la imprima en el serial ni en GitHub. Revise el firmware de conectividad UNO R4 WiFi y el almacén de certificados de confianza de su versión usando el manual oficial de Arduino y las herramientas de actualización correspondientes.

La compatibilidad de la cadena de confianza con UNO R4 WiFi varía con el firmware y CA. Esta guía no ha probado el handshake físico con esa placa ni dispone de los modelos de sensores. No deshabilite la validación de certificado o hostname para resolver errores. import math

DEFAULTS = {
    'soil_moisture': {'min': 25, 'max': 65, 'h': 3, 'enabled': True},
    'temperature': {'min': 15, 'max': 30, 'h': 1, 'enabled': True},
    'soil_ec': {'min': 0.5, 'max': 2.5, 'h': 0.1, 'enabled': True},
    'water_ph': {'min': 5.5, 'max': 7.5, 'h': 0.2, 'enabled': True},
}
RANGES = {'soil_moisture': (0,100), 'temperature': (-40,125), 'soil_ec': (0,100), 'water_ph': (0,14)}
DECISIONS = {
 'soil_moisture': ('Evaluar inicio de riego', 'Evaluar detención de riego'),
 'temperature': ('Revisar temperatura baja', 'Revisar estrés térmico'),
 'soil_ec': ('Revisar nutrientes y calibración', 'Revisar salinidad'),
 'water_ph': ('Revisar acidez', 'Revisar alcalinidad'),
}

def number(v):
    if isinstance(v, bool) or not isinstance(v, (int,float)) or not math.isfinite(v):
        raise ValueError('Se requiere número finito')
    return float(v)

def validate_rules(rules):
    if not isinstance(rules, dict) or set(rules) != set(DEFAULTS):
        raise ValueError('Se requieren cuatro reglas')
    result = {}
    for k, r in rules.items():
        if not isinstance(r,dict) or set(r) != {'min','max','h','enabled'} or not isinstance(r['enabled'],bool):
            raise ValueError('Regla inválida: '+k)
        lo, hi, h = (number(r[n]) for n in ('min','max','h'))
        a,b=RANGES[k]
        if not (a <= lo < hi <= b and 0 <= h <= (hi-lo)/2):
            raise ValueError('Límites o histéresis inválidos: '+k)
        result[k] = {'min':lo,'max':hi,'h':h,'enabled':r['enabled']}
    return result

def state(value, rule, previous='NORMAL'):
    if not rule['enabled']: return 'DISABLED'
    lo,hi,h=rule['min'],rule['max'],rule['h']
    if value < lo: return 'LOW'
    if value > hi: return 'HIGH'
    if previous == 'LOW' and value < lo+h: return 'LOW'
    if previous == 'HIGH' and value > hi-h: return 'HIGH'
    return 'NORMAL'

def evaluate(values, rules, previous):
    states, events = {}, []
    for k,v in values.items():
        before=previous.get(k,'NORMAL')
        after=state(v,rules[k],before)
        states[k]=after
        if after != before:
            decision = DECISIONS[k][0 if after=='LOW' else 1] if after in ('LOW','HIGH') else ('Recuperación del rango' if after=='NORMAL' else 'Alarma deshabilitada')
            events.append({'sensor':k,'from':before,'to':after,'value':v,'decision':decision})
    return states,events

def parse(topic,payload):
    p=topic.split('/')
    if len(p)!=3 or p[0]!='irrigation' or p[2]!='telemetry' or not re.fullmatch(r'[A-Za-z0-9_-]{1,64}',p[1]): raise ValueError('topic')

    vals={}

        v=number(d.get(k))
        if not lo<=v<=hi: raise ValueError(k)
        vals[k]=v
    return p[1],boot,seq,vals

    except DuplicateKeyError: pass
    except Exception:
        logging.exception('Fallo de persistencia; reiniciar sin ACK')
        # El proceso sale; Compose lo reinicia. Sesión MQTT persistente.
        os._exit(1)
    if m.qos: c.ack(m.mid,m.qos)
